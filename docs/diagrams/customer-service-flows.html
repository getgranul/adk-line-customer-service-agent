1. 訊息處理與記憶分層

一則訊息的處理時序

記憶與 Context 分開設計

保存的內容負責什麼不能拿來代替什麼
案件狀態誰可以處理、模式、revision、真人認領。狀態切換必須由後端與資料庫交易控制。模型 Prompt 與特殊文字 Tag 無法提供跨執行個體的互斥控制。
完整訊息紀錄客人、AI、真人原文，作為客服畫面、稽核與重新整理 Context 的來源。保存全部原文，不代表每輪都要送全部原文給模型。
ADK Session 與 State同一案件中的模型互動、工具事件與對話工作資料，存在 Vertex AI 代管的 Session，重啟後能還原。案件狀態不存在 Session 的 state。Firestore 的案件資料不能代替 ADK Session；ADK 內建的 SessionService 沒有 Firestore 版本。
跨 Session 記憶結案時交給 Vertex AI Memory Bank 抽取，自訂主題只允許偏好、未解決問題、聯絡限制，並以客戶身分為範圍隔離；訂單與權益仍重新查詢。不能把上一個案件的未驗證推測、舊政策或舊權益當成目前事實。
模型 Context本輪問題＋最近對話＋案件摘要＋經授權的訂單與政策片段，限制 token 預算。大型 Context Window 不能代替摘要策略、事實保存與長對話評估。

同一案件跨服務重啟仍延續；明確結案後的新聯絡建立新案件與 Session，再按權限讀取必要的跨案件記憶。長對話用 ADK 的 EventsCompactionConfig 把舊對話摘要成一段，之後只送摘要加最近幾輪。

2. Agent 處理流程：會員分流由後端約束

  1. 模型不能自行提升權益。Tool 由後端綁定可信客戶身分；使用者說「我是 VVIP」或輸入別人的訂單編號，都不能改變查詢權限。Tool 回傳結構化結果，後端選擇可用的政策範圍。
  2. 檢索邊界由程式限制。一般會員只能取得適用的一般條款；VVIP 的免運策略由後端提供。模型負責組織文字，工具與檢索函式再次檢查權限。權限檢查寫在工具與檢索函式裡，不寫在提示詞。
  3. VVIP 的順序：由程式依會員等級觸發，不由模型決定。先切換轉接準備狀態，封鎖一般 AI 回覆；授權指定政策回覆；該階段結束後進入等待真人，非同步通知客服。發送失敗也不能自動回到 AI 模式。
  4. 情緒與能力判斷仍需評估。明確要求真人可用確定規則；嚴重情緒與能力不足可結合分類與工具結果，需用案例測試誤判率。模型不得只靠輸出特殊 Tag 改變案件狀態。

state machine 的布林判斷本身不構成併發鎖。「發送前再檢查」用 Firestore 交易比對模式與 revision，通過才寫入待發送紀錄；重試沿用同一筆待發送紀錄與同一把重試鍵。已交給外部 API 的訊息無法靠狀態切換撤回。

3. 客服 state machine：眼前這一步在做什麼

把「AI 能不能處理與回覆」寫成可測試的規則。相同規則之後供本機模擬、LINE 入口、ADK Worker 與客服網頁共用。

revision 的例子：AI 在版本 0 開始生成，客人要求真人後變成版本 1。舊工作完成時拿版本 0 比對最新狀態，就應放棄回覆；之後真人交回 AI，版本繼續增加，舊回覆也不會重新有效。

state machine 只定義合法切換與回覆判斷。客服身分驗證、認領者權限、資料庫交易、訊息排序與發送去重，由應用服務與持久化層負責；state machine 的單元測試不能證明分散式環境下的安全。

這份文件只描述設計，不記錄完成狀態。

官方機制查核：ADK Session／State／Memory 分別管理單次互動與跨 Session 資訊，內建 SessionService 只有記憶體、Vertex AI 與關聯式資料庫三種；ADK Context compression 提供 Context 壓縮配置；Cloud Run 預設只在處理請求時配置 CPU，Cloud Tasks 以受驗證請求執行非同步工作；LINE 在 2 秒內沒收到 webhook 回應記為逾時；push 支援重試鍵，24 小時內同一把鍵重傳不會重複傳送；push 計入每月訊息額度；BigQuery 同一張表的並行交易會直接失敗。
