1. 部署架構：訊息如何抵達 Agent 與真人

一則訊息的處理時序

記憶與 Context 分開設計

保存的內容負責什麼不能拿來代替什麼
案件狀態誰可以處理、模式、revision、真人認領。狀態切換必須由後端與資料庫交易控制。模型 Prompt 與特殊文字 Tag 無法提供跨執行個體的互斥控制。
完整訊息紀錄客人、AI、真人原文，作為客服畫面、稽核與重新整理 Context 的來源。保存全部原文，不代表每輪都要送全部原文給模型。
ADK Session 與 State同一案件中的模型互動、工具事件與對話工作資料，存在 Vertex AI 代管的 Session；需通過重啟與還原測試。Firestore 的案件資料不能代替 ADK Session；ADK 內建的 SessionService 沒有 Firestore 版本。
跨 Session 記憶結案時交給 Vertex AI Memory Bank 抽取，自訂主題只允許偏好、未解決問題、聯絡限制，並以客戶身分為範圍隔離；訂單與權益仍重新查詢。不能把上一個案件的未驗證推測、舊政策或舊權益當成目前事實。
模型 Context本輪問題＋最近對話＋案件摘要＋經授權的訂單與政策片段，限制 token 預算。大型 Context Window 不能代替摘要策略、事實保存與長對話評估。

同一案件跨服務重啟仍延續；明確結案後的新聯絡建立新案件與 Session，再按權限讀取必要的跨案件記憶。ADK 的壓縮設定與摘要策略，在確定 SDK 版本後實作。

2. Agent 處理流程：會員分流由後端約束

  1. 模型不能自行提升權益。Tool 由後端綁定可信客戶身分；使用者說「我是 VVIP」或輸入別人的訂單編號，都不能改變查詢權限。Tool 回傳結構化結果，後端選擇可用的政策範圍。
  2. 檢索邊界由程式限制。一般會員只能取得適用的一般條款；VVIP 的免運策略由後端提供。模型負責組織文字，工具與檢索函式再次檢查權限。具體 ADK callback 與工具包裝在 SDK 版本確認後實作。
  3. VVIP 的順序：先切換轉接準備狀態，封鎖一般 AI 回覆；授權指定政策回覆；該階段結束後進入等待真人，非同步通知客服。發送失敗也不能自動回到 AI 模式。
  4. 情緒與能力判斷仍需評估。明確要求真人可用確定規則；嚴重情緒與能力不足可結合分類與工具結果，需用案例測試誤判率。模型不得只靠輸出特殊 Tag 改變案件狀態。

「發送前再檢查」尚未實作；狀態機的布林判斷本身不構成併發鎖。後續必須以交易式發送授權與待發送紀錄控制重試；已交給外部 API 的訊息無法靠狀態切換撤回。

3. 客服狀態機：眼前這一步在做什麼

把「AI 能不能處理與回覆」寫成可測試的規則。相同規則之後供本機模擬、LINE 入口、ADK Worker 與客服網頁共用。

revision 的例子：AI 在版本 0 開始生成，客人要求真人後變成版本 1。舊工作完成時拿版本 0 比對最新狀態，就應放棄回覆；之後真人交回 AI，版本繼續增加，舊回覆也不會重新有效。

目前程式只定義合法切換與回覆判斷。客服身分驗證、認領者權限、資料庫交易、訊息排序與發送去重，仍要在應用服務與持久化層完成；不能只憑這九項單元測試宣告生產環境已安全。

4. 實作相依圖：先完成什麼，才能接什麼

建置順序與每一步的驗收

工作前提與產出通過標準
本機基礎與驗簽現有 Python 虛擬環境、HTTP 入口與原始內容簽章驗證。已取得 /healthz HTTP 200，以及使用者回報的六項測試 OK。
客服狀態規則現有狀態機；先驗證合法切換與舊 AI 回覆失效。九項新增測試待執行；加上驗簽應共十五項通過。這只驗證純規則，不證明分散式競爭已解決。
本機流程與持久化狀態規則通過後，先用合成事件、明確標為測試用的儲存介面走流程，再接 Firestore；定義資料模型與交易。ADK Session 由 Vertex AI 代管，不在 Firestore 實作。同案件訊息能保存、重啟能還原、不同客人無法互查訂單；相同事件重送不造成重複處理。測試替身不能作為雲端完成證據。
ADK、Tools 與條款檢索先改用 uv 並安裝 ADK、建立 LINE 客服專用的 GCP 專案；合成會員與訂單、腳本產生的條款 PDF 與建置時索引、Vertex AI Session 與 Memory Bank；工具使用可信身分，不接受模型自行指定客戶。一般會員與 VVIP 回答符合各自政策；查別人訂單被拒；多輪追問、代名詞與跨案件必要記憶可驗證；長對話受 Context 預算限制。
真人客服網頁共用案件與訊息服務，加入登入、認領者驗證與發送介面。真人完整看到客人與 AI 訊息；真人回覆保存；兩位客服不能同時認領；只有授權客服能釋放案件或結案。
LINE 串接測試帳號準備好後再做。既有驗簽接上 Webhook，加入事件去重與身分綁定。原始內容先驗簽再解析；未可靠保存與安排工作前不確認接收；測試事件可處理，真實客戶事件可回覆。
佇列與雲端部署本機流程通過後，接 Cloud Tasks、Worker IAM、push 發送、BigQuery 處理事件與監控，再整合兩個 Cloud Run 服務。重試不重複副作用、異常可追蹤、同案件工作有排序與互斥；真人切換後禁止新 AI 發送授權，並量測在途訊息的邊界。
Showcase 與評估真實 LINE、一般／VVIP 合成身分與客服網頁；準備固定問題集與操作劇本。展示四個目標，記錄正確率、越權阻擋、轉接後誤回覆、回覆時間、模型 token 與費用；報告實測結果，不預填達標數字。

維護與擴充如何分工

domain/ 放案件與權限規則；後續的應用服務串接儲存、Agent 與發送介面；api/ 處理 HTTP；integrations/ 包裝 LINE、Firestore、Vertex AI 與 BigQuery 等外部服務。只有前述既有目錄與狀態機已存在，其餘仍待建置。

未來 MCP 只包裝相同業務服務；主動式客服可由 Scheduler 觸發另一個工作入口，共用工具、訂單權限、發送限流與紀錄。另行檢查主動訊息的使用者同意、可推播資格與去重，不直接重播被動客服 Prompt。
